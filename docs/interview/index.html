Overview

VahanOne is structured as a decoupled three-tier multi-tenant web platform containerized with Docker and Docker Compose. It separates client-side SPA rendering, RESTful business logic and scheduling, and relational data storage.

Architectural Highlights

1. **Containerized Network**: In local development and Docker Compose, services communicate over an internal bridge network (`db:5432` and `backend:8000`), with only ports 80 (Frontend) and 8000 (Backend) exposed to the host machine.

2. **Reverse Proxying**: In production Docker, Nginx acts as an HTTP server serving built SPA assets and redirecting all unhandled paths to `/index.html` to support HTML5 client-side history routing.

3. **Dual API Handling**: FastAPI handles native structured CRUD routers with Pydantic validation while concurrently serving a PostgREST-compatible translation engine (`/rest/v1/*`) to support client-side data querying without cloud dependencies.

Overview

VahanOne enforces a strict clean separation of concerns in the backend:

`HTTP Request -> Router -> Pydantic Schema Validation -> Service Layer (Business Logic & Conflicts) -> Repository / ORM -> Database Engine -> Response Model`.

Below is a detailed trace of a real core endpoint: `POST /bookings/` (Creating a new vehicle booking).

Architectural Highlights

  • **Fail-Fast Validation**: Pydantic validates data types, date relationships, and negative numbers before any database connection is exercised.
  • **Tenant Context Injection**: `organization_id` is never trusted from the client payload for data mutation; it is pulled directly from the validated JWT token inside the dependency layer.
  • **Encapsulated Business Invariants**: Complex business rules (like checking driver availability and preventing scheduling during maintenance windows) reside strictly in `booking_service.py`, leaving routers thin and testable.

    Overview

    VahanOne implements a **shared-database, pooled-schema multi-tenant architecture**. Each tenant is represented as an `Organization`. Every business entity (vehicles, drivers, bookings, invoices) contains an `organization_id` foreign key. Tenant isolation is enforced at the application layer via JWT claims and database indexes, supplemented by PostgreSQL Row-Level Security (RLS) where applicable.

    Security Invariants

    1. **Zero Trust Client Identity**: The frontend cannot alter its tenant context. Every mutation relies strictly on `current_user.organization_id` derived cryptographically from the signed JWT access token.

    2. **Compound Unique Constraints**: Uniqueness is scoped per tenant, not globally. For example:

  • `UniqueConstraint('organization_id', 'vehicle_number', name='uq_vehicle_org_number')`
  • `UniqueConstraint('organization_id', 'phone_number', name='uq_customer_org_phone')`

    • This allows different transport companies to register standard local vehicle plates without collision.

    3. **Token Invalidation**: Refresh tokens include a `refresh_token_version` integer column on the user table. Changing this integer immediately invalidates all active sessions for that user.

    Overview

    VahanOne operates on a normalized PostgreSQL schema with 27 relational tables. Core entities derive from three architectural base mixins:

  • `TimestampMixin`: `created_at`, `updated_at` (automatic UTC timestamps)
  • `TenantMixin`: `organization_id` (UUID foreign reference isolating every record)
  • `SoftDeleteMixin`: `deleted_at` (preserving audit history on customers, vehicles, drivers)

    • Key Schema Design Decisions

    1. **Financial Integrity**: Money amounts in Invoices, Trips, and Expenses use `Numeric(12, 2)` for precision, while Payment transactions use `BigInteger amount_cents` to eliminate floating-point rounding errors.

    2. **Double Linkage (Bookings & Trips)**: An Invoice links to both `customer_id` and optional `trip_id` / `booking_id`. This allows invoicing ad-hoc direct bookings as well as multi-leg trip contracts.

    3. **Soft Deletions**: Deleting a vehicle or driver preserves historical booking and trip revenue calculations via `deleted_at IS NULL` query filters.

    The VahanOne booking lifecycle orchestrates customer reservations from creation through vehicle conflict checking, dispatch, odometer execution, financial calculation, and invoice generation.

    Detailed Lifecycle Sequence

    Edge Cases Handled in Code

    1. **Odometer Rollback Prevention**: `end_km` must be strictly `>= start_km`, else returns `HTTP 400 Bad Request`.

    2. **Duplicate Active Trip Prevention**: `_assert_no_active_trip_for_booking` prevents dispatching multiple concurrent trips for the same booking.

    3. **Double Maintenance Check**: A vehicle under scheduled maintenance cannot be booked, and maintenance cannot be scheduled over an active confirmed booking.

    Overview

    VahanOne provides an automated invoicing and tax calculation engine tailored to Indian transport logistics. It transforms completed trips into GST-compliant invoices with line items, deductions for advance payments, and payment state machines.

    Mathematical Formulae

    $$\text{Subtotal} = \text{Package Amount} + (\text{Extra KM} \times \text{Rate}) + (\text{Extra Hours} \times \text{Rate}) + \text{Driver Bata} + \text{Toll} + \text{Night Charges}$$

    $$\text{Total Invoice Amount} = \text{Subtotal} + \text{Tax Amount}$$

    $$\text{Balance Due} = \text{Total Invoice Amount} - \text{Advance Received}$$

    Security & Concurrency Highlights

    1. **Invoice Number Gap Prevention**: Sequential generation queries existing non-deleted numbers for the organization, finding the lowest available sequential index starting from `10001`.

    2. **Double-Invoicing Guard**: A Unique Constraint on `(organization_id, trip_id)` and an explicit application check prevent multiple invoices against the same trip.

    3. **Immutability of Settled Invoices**: Once status transitions to `PAID`, all `PUT /invoices/{id}` updates are blocked with `HTTP 400 Bad Request`.

    Overview

    The VahanOne Profit Engine bridges operational logistics with financial viability. It computes granular profitability across two orthogonal dimensions:

    1. **Per-Trip Level**: Comparing realized trip billing against direct variable operating costs (fuel, tolls, driver bata, parking).

    2. **Per-Vehicle Level**: Aggregating daily and monthly profit timelines to help fleet owners identify underperforming or high-maintenance vehicles.

    Calculation Formulas

    $$\text{Trip Revenue} = \text{Package Amount} + (\text{Extra KM} \times R_{\text{km}}) + (\text{Extra Hours} \times R_{\text{hr}}) + \text{Bata} + \text{Night} + \text{Toll}$$

    $$\text{Total Expenses} = \sum \text{Fuel} + \sum \text{Toll} + \sum \text{Parking} + \sum \text{Maintenance} + \sum \text{Misc}$$

    $$\text{Net Profit}_{\text{Trip}} = \text{Trip Revenue} - \text{Total Expenses}$$

    $$\text{Monthly Vehicle Profit} = \sum_{i=1}^{N_{\text{trips}}} \text{Trip Profit}_i$$

    Performance & Optimization Notes

  • **Instant Recalculation**: Every time a new expense is logged (`POST /expenses/`) or a trip is completed (`POST /trips/{id}/complete`), `profit_service.recalculate_trip_profit` runs synchronously within the transaction.
  • **Aggregated Projections**: The system caches daily and monthly totals in `vehicle_daily_profit` and `vehicle_monthly_profit` tables. This guarantees $O(1)$ response times for the front-end monthly charts without scanning millions of individual trip records.

    VahanOne features an automated compliance and document expiry monitoring engine. It protects transport operators against heavy regulatory fines and vehicle impoundment under the Indian Motor Vehicles Act by tracking statutory renewals (RC, FC, Insurance, National Permits, PUC, Road Tax, EMI).

    [!NOTE]
    **Code vs. README Discrepancy**: While the original README mentions `APScheduler`, the production codebase executes a dedicated Python background daemon thread (`backend/app/services/reminder_scheduler.py`) using `threading.Thread` with a configurable sleep interval (`settings.reminder_scheduler_interval_minutes = 60`), guaranteeing lightweight execution without external broker dependencies.

    Compliance Threshold Matrix

    | Statutory Document | Standard Indian Validity | System Warning Thresholds | Risk if Unaddressed |

    | :--- | :--- | :--- | :--- |

    | **Vehicle Insurance** | 1 Year (Comprehensive/Third-party) | **30 days, 15 days, 7 days** | Vehicle impounded; claims denied |

    | **Fitness Certificate (FC)** | 1–2 Years (Commercial Vehicles) | **30 days, 15 days, 7 days** | Seizure of registration certificate |

    | **State / National Permit** | 1–5 Years | **30 days, 15 days, 7 days** | Heavy inter-state border penalties |

    | **Pollution (PUC)** | 6 Months | **15 days, 7 days, 1 day** | ₹10,000 fine under amended MV Act |

    | **Road Tax** | Quarterly / Annual | **30 days, 15 days, 7 days** | Compound penalty interest |

    | **Vehicle Loan EMI** | Monthly | **7 days, 3 days, Due Date** | Credit rating penalty; repossession risk |

    Deduplication Strategy

    To avoid bombarding fleet managers with duplicate notifications every 60 minutes, the query explicitly checks:

    ```python

    existing = reminder_repository.find_existing_reminder(

    db,

    organization_id=org_id,

    rule_id=rule.id,

    entity_type="vehicle",

    entity_id=vehicle.id,

    due_date=due_date

    )

    ```

    If an active or acknowledged reminder already exists for that specific due date, the scheduler idempotently skips creating another.

    Overview

    The VahanOne user interface is built as a single-page application (SPA) with **React 18**, **Vite**, **TypeScript**, and **Tailwind CSS**. It emphasizes responsive, low-latency fleet operations, optimistic client updates, token refresh management, and defensive error boundaries.

    State Management & Invariants

    1. **No External Redux Overhead**: Local and custom hook state (`useState`, `useEffect`, `useCallback`) is used to keep bundle size small and render times instantaneous.

    2. **Silent Refresh Interceptor**: `lib/api.ts` implements a subscriber queue (`subscribeTokenRefresh` and `onRefreshed`). If multiple parallel requests fail with `401`, only a single `POST /auth/refresh` is dispatched; upon resolution, all waiting requests retry seamlessly without user disruption.

    3. **Dual Protocol Compatibility**: Frontend can communicate directly with FastAPI REST endpoints (`/bookings`, `/trips`) as well as the Supabase compatibility endpoints (`/rest/v1/*`), allowing seamless interoperability regardless of deployment target.

    Overview

    The VahanOne deployment lifecycle ensures that every commit pushed to GitHub is automatically linted, type-checked, tested, built, containerized, and deployed to production cloud infrastructure with zero downtime.

    Production Pipeline Stages

    1. **Linting & Hygiene**: `flake8` enforces PEP8 formatting rules and catches undefined symbols and circular imports before any deployment begins.

    2. **Type Safety Verification**: `tsc --noEmit` verifies strict TypeScript typing across all components, interfaces, and API responses.

    3. **Database Migration Synchronization**: Database schema changes are version-controlled via Alembic revisions (`alembic/versions/`). During container boot or Render deployment, `alembic upgrade head` runs automatically before the web server begins accepting HTTP traffic.

    4. **Zero-Downtime Deployment**: Render creates the new container instances, waits for HTTP `GET /` to return `200 OK`, and then swaps the DNS router to the new container without dropping in-flight client requests.
